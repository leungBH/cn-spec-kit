# Step 5: 需求文档生成 (requirement)

> **位置**：在 Step 4 需求追问 之后、Step 6 PRD 之前。
> **目的**：在产出正式 PRD 之前，先按用户选择的"需求文档模板"生成一份正式的需求文档（售前/SDD 等格式），用于客户/业务方评审、签字归档或与 AI SDD 环境对接。

---

## 执行步骤

### 5.1 加载可用模板清单

1. 读取 `templates/index.md`，获取所有可用模板的元数据（id / name / description / 章节预览）
2. 如果在 `presets/<industry>/` 中存在 `<id>.md` 覆盖文件，标注为"已定制"
3. 以结构化提问方式向用户展示模板列表，每个选项包含模板名 + 适用场景 + 章节预览

**提问模板**：

```json
{
  "questions": [
    {
      "header": "需求模板",
      "question": "请选择本次需求使用的需求文档模板",
      "multiSelect": false,
      "options": [
{
          "label": "AI SDD 标准化需求文档",
          "description": "面向 AI 辅助开发环境，按数据/流程/功能开发分类，字段级可追溯、可自动生成代码"
        }
      ]
    }
  ]
}
```

> **如果模板数量 ≥ 3 个**，按 index.md 的顺序展示前 3 个 + "查看更多"。
> **如果用户选择了"暂不选择"**，使用 `index.md` 中的"默认模板选择规则"自动推荐。

### 5.2 加载模板源文件

按覆盖优先级查找用户选择的 `<id>` 模板源文件：

```
1. presets/<industry>/<id>.md     行业预设（行业名从 01-discovery.md 中获取）
2. templates/<id>.md              全局默认
```

### 5.3 收集输入

- `00-brief.md`（原始一句话需求）
- `01-discovery.md`（7 维度需求发现 + Step 4 追问补充）
- （如已存在）`02-competitive-research.md` 中"建议补充"的功能点

### 5.4 填充模板生成需求文档

按模板的章节结构逐章填充：

- **章节标题、字段名称、表格列名**：保持模板原文，不修改
- **"示例"段落**：根据 `01-discovery.md` 实际内容改写为本次需求的内容
- **"填写要求"段落**：保留原文（这是给阅读者的填写规范，需求文档定稿后也要保留）
- **"{{占位符}}"字段**：根据 `01-discovery.md` 实际内容替换；无法替换的标记为"待补充"
- **空表格**：根据 discovery 内容填写实际行；如确实无内容则保留表头 + "暂无"

**章节裁剪规则（针对 requirement-sdd）**：

`requirement-sdd` 模板按"开发类型"裁剪：

| 开发类型 | 保留的章节 |
|----------|------------|
| 数据开发 | 需求背景 + 数据开发需求（完整保留）+ 验收标准 |
| 流程开发 | 需求背景 + 流程开发需求（完整保留）+ 验收标准 |
| 功能开发 | 需求背景 + 功能开发需求（完整保留）+ 验收标准 |
| 综合 | 多个开发类型模块（按需选择） |

### 5.5 写入产物

产物文件名固定为 `03-requirement.md`，写入 `specs/<序号-功能名>/`：

- 文件开头追加一行 frontmatter 记录使用的模板：
  ```
  <!-- 模板: <id> | 模板来源: <presets|templates>/<path> -->
  ```

### 5.6 记录用户选择

在 `00-brief.md` 末尾追加（如果不存在则创建）"模板选择记录"小节：

```markdown
## 模板选择记录

| 步骤 | 选择项 | 模板ID | 选择时间 |
|------|--------|--------|----------|
| Step 5 | 需求文档模板 | <id> | <YYYY-MM-DD HH:mm> |
```

## 产物说明

### 03-requirement.md 的作用

- **售前场景**：作为给客户演示 / 评审 / 签字的正式需求文档
- **SDD 场景**：作为 AI 辅助开发环境的输入，字段级可追溯
- **后续步骤的输入**：
  - Step 6 PRD 直接基于 `03-requirement.md` 抽取结构化内容
  - 验收标准、研发任务中的字段引用都从 `03-requirement.md` 中来

### 产物优先级

- **必须生成**：当用户在 Step 1 选择"客户需求到演示 Demo 类"或包含"需求文档"等关键词时
- **可选生成**：当用户明确说"跳过需求文档，直接做 PRD"时，可不生成

## 🚪 质量门禁

### 第一层：步骤完整性门禁

读取 `checklists/requirement-checklist.md`，逐条对照 `03-requirement.md`：

- 覆盖率 ≥ 90%：✅ 通过，进入 Step 6
- 覆盖率 70%-89%：⚠️ 基本通过，列出缺失项供用户确认
- 覆盖率 < 70%：❌ 回到本步修补

**门禁要点**：
1. **必填字段完整性**：基础信息表 12 个字段无空值
2. **章节结构完整性**：所选模板的核心章节无缺失
3. **示例已替换**：所有"示例"段落已替换为本次实际内容
4. **占位符清理**：所有 `{{...}}` 占位符已替换或显式标注"待补充"
5. **章节裁剪合规**：根据需求类型正确裁剪多余章节

### 第二层：跨步骤一致性检查

内部门禁通过后，执行跨产物一致性校验（详见 `steps/consistency-checks.md`）：

| 检查项 | 严重级别 | 说明 |
|--------|----------|------|
| CC-08: 需求文档角色 ↔ Discovery干系人 | 🔴 阻塞 | 角色列表必须对齐 |
| CC-09: 需求文档验收指标 ↔ Discovery成功指标 | 🔴 阻塞 | 验收指标必须有对应 |

- 🔴 阻塞级不一致：必须修复后才能继续
- 🟡 警告级（如有）：列出差异供用户确认

### 第三层：外部大模型评审

一致性检查通过后，触发外部大模型评审（详见 `steps/external-review.md`）：

- 重点评审维度：设计合理性(30%) + 业务逻辑(30%) + 可落地性(20%)
- 典型质疑方向：需求描述是否具体到字段级？验收指标是否可测试？章节裁剪是否遗漏关键需求？
- 通过标准：总分 ≥ 75 且无🔴严重问题
- 不通过：根据评审意见修补需求文档，最多重试 3 轮
- 评审结果记录到 `14-review-log.md`

### 第四层：人类QA确认门

外部评审通过后（或⚠️通过但需关注），**必须暂停等待人类确认**才能进入 Step 6。

以结构化提问方式向用户展示本步骤产物摘要和评审发现的问题：

```json
{
  "questions": [
    {
      "header": "QA确认",
      "question": "Step 5 需求文档已完成，四层质量检查结果如下：\n\n**内部门禁**: ✅通过 / ⚠️基本通过（覆盖率XX%）\n**一致性检查**: ✅通过 / 🟡有差异需关注\n**外部评审**: ✅通过 / ⚠️通过但需关注 / ❌不通过\n\n**产物关键摘要**:\n- <3-5条：模板类型、核心角色列表、主要功能模块、验收指标概要>\n\n**外部评审发现的问题**:\n- 🔴 <严重问题1>\n- 🟡 <需关注问题1>\n- 💡 <优化建议1>\n\n请确认是否可以进入下一步？",
      "multiSelect": false,
      "options": [
        {
          "label": "✅ 确认通过，进入 Step 6",
          "description": "产物质量可接受，评审发现的问题可后续迭代处理"
        },
        {
          "label": "🔧 需要修改，指出调整内容",
          "description": "产物存在需要修改的问题，请在'Other'中说明需要调整什么"
        }
      ]
    }
  ]
}
```

- 用户选择"确认通过" → 记录确认结果到 `14-review-log.md`，进入 Step 6
- 用户选择"需要修改" → 根据用户反馈修改 `03-requirement.md`，重新执行内部门禁+外部评审+人类确认（不重算重试轮次，人类确认不算在3轮重试内）
- 用户未回应时 → **不能自动进入下一步**，必须等待

外部评审通过后，才能触发人类QA确认。

## 跨步骤影响

### 上游

- 接收 Step 2 产出的 `01-discovery.md`（7 维度需求发现）
- 接收 Step 4 产出的追问补充内容（已合并入 `01-discovery.md`）
- （可选）接收 Step 3 产出的 `02-competitive-research.md`

### 下游

- **Step 6 PRD**：直接读取 `03-requirement.md` 抽取业务背景、角色、功能清单、验收标准等
- **Step 11 验收标准**：从 `03-requirement.md` 的"验收标准"章节抽取量化指标
- **Step 12 研发任务**：从 `03-requirement.md` 的接口字段、流程节点中拆分任务

### 一致性检查

Step 6 开始前必须检查：
- 角色定义一致性：`03-requirement.md` 中的角色列表 vs `01-discovery.md` 中的干系人
- 验收标准一致性：`03-requirement.md` 中的验收指标 vs `01-discovery.md` 中"成功指标"

如有差异，🔴 阻塞：必须回到 Step 5 修正。

## 单步执行

如果用户只想要"生成需求文档"而不走完整流程：

1. 提示用户提供原始需求（brief）
2. 询问模板选择
3. 跳过 Step 2/3/4，直接基于 brief + 用户回答 5.1 步骤中的元数据填充模板
4. 写入 `03-requirement.md`（此时无前置步骤，文件直接放在用户指定的目录下）

## Guardrails

- 模板选择必须由用户确认，不能自动决定
- 所选模板的章节结构必须严格遵守，不允许随意删减（只允许按"章节裁剪规则"裁剪不适用部分）
- 模板的"填写要求"段落必须保留在产物中（这是文档的填写规范说明）
- 示例内容必须替换为本次需求实际内容，不允许直接复制示例
- `{{占位符}}` 必须显式替换或标注"待补充"，不允许保留未替换
- 产物文件命名固定为 `03-requirement.md`，不允许用户自定义
- 一个 spec 目录只允许存在一个 `03-requirement.md`（如选择不同模板需重新生成，必须先删除旧文件）
