# 外部大模型评审机制 (external-review)

> **位置**：每个 Step 产物完成后、内部质量门禁通过后，自动触发外部大模型评审。
> **目的**：借助外部大模型的独立视角评审每步产物质量，通过后才进入下一步，不通过则根据评审意见优化产物，直到通过。

---

## 1. 外部大模型注册

外部大模型通过 **OpenAI Chat Completions 格式** 注册，用户需提供 3 个参数：

| 参数 | 说明 | 示例 |
|------|------|------|
| `url` | API 基础 URL（不含 `/chat/completions` 路径） | `https://token.bayesdl.com/api/maas/v1/anthropic` |
| `key` | API Key | `sk-897f460487844814b5f71bf02816be75` |
| `model` | 模型名称 | `claude-sonnet-4-20250514` |

### 注册方式

用户通过 `AskUserQuestion` 提供配置，或在项目根目录创建 `.cn-spec-kit-llm.json` 配置文件：

```json
{
  "reviewers": [
    {
      "name": "评审员1-Claude",
      "url": "https://token.bayesdl.com/api/maas/v1/anthropic",
      "key": "sk-xxxxxxxxxx",
      "model": "claude-sonnet-4-20250514"
    },
    {
      "name": "评审员2-GLM",
      "url": "https://token.bayesdl.com/api/maas/v1/anthropic",
      "key": "sk-yyyyyyyyyy",
      "model": "glm-5.1"
    }
  ]
}
```

**多评审员策略**：
- 如果注册了 1 个评审员：该评审员的评审结果决定是否通过
- 如果注册了 2+ 个评审员：每个评审员独立评审，≥50% 通过即视为通过（如 2 个评审员中至少 1 个通过）
- 如果没有注册评审员：跳过外部评审，仅执行内部质量门禁

---

## 2. 评审调用方式

使用 Bash 工具执行 curl 命令调用外部大模型 API：

```bash
curl -s -X POST "<url>/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <key>" \
  -d '{
    "model": "<model>",
    "messages": [
      {"role": "system", "content": "<评审系统提示>"},
      {"role": "user", "content": "<产物内容 + 评审要求>"}
    ],
    "temperature": 0.3,
    "max_tokens": 2048
  }'
```

**注意**：
- URL 路径拼接规则：`url` + `/chat/completions`。如果 `url` 已包含 `/chat/completions`，不再追加
- 请求格式严格遵循 OpenAI Chat Completions API 规范
- 响应解析：从 `response.choices[0].message.content` 中提取评审结果

## 3. 评审流程

每个 Step 产物完成后，执行以下评审流程：

```
产物生成 → 内部质量门禁 → 外部大模型评审 → 通过/不通过
                                              ↓ 不通过
                                          根据评审意见优化 → 重新内部门禁 → 重新外部评审
                                              ↓ 通过（最多重试3轮）
                                          记录评审结果 → 进入下一步
```

### 3.1 评审触发时机

| Step | 产物 | 评审内容 |
|------|------|----------|
| Step 2 | 01-discovery.md | 需求发现的 7 维度覆盖完整性、业务理解准确性 |
| Step 3 | 02-competitive-research.md | 竞品调研的深度、功能借鉴的合理性 |
| Step 4 | 01-discovery.md 追问补充 | 阻塞维度是否明确回答、追问是否充分 |
| Step 4.5 | 03-requirement.md | 需求文档的完整性、模板合规性、占位符清理 |
| Step 5 | 04-prd.md | PRD 结构完整性、功能优先级合理性、竞品融入充分度 |
| Step 6 | 05-scope-selection.md | 用户确认即可（无需外部评审） |
| Step 7 | 06-dependency-dag.md + 07-business-flow.md | 依赖关系合理性、流程完整性、审批规则完备 |
| Step 8 | 08-page-spec.md | 页面规格要素完整性、角色视图覆盖度 |
| Step 9 | 10-permission-matrix.md | 权限矩阵完备性、操作覆盖度 |
| Step 10 | 11-acceptance.md | 验收场景覆盖度、边界条件充分度 |
| Step 11 | 12-dev-tasks.md + 13-traceability-matrix.md | 任务拆解粒度合理性、追踪矩阵完整性 |

**Step 6（开发范围选择）不需要外部评审**，因为是用户手动确认的步骤。

### 3.2 评审系统提示模板

**核心定位**：评审员不是做完整性检查（那由内部门禁负责），而是**以资深产品专家的视角评审设计合理性**，主动发现问题、提出质疑、给出改进方向，驱动产物迭代优化。

每个评审调用都使用统一的系统提示模板，根据产物类型调整评审维度：

```
你是一位拥有10年+ToB产品经验的资深产品评审专家。你的任务是以专业视角评审以下产品规格文档的设计合理性，**主动发现问题和风险**，而非仅做格式完整性检查。

评审原则：
1. **质疑优先**：不要默认认可，而是主动寻找设计缺陷、逻辑漏洞、业务风险
2. **问题驱动**：评审的核心产出是"发现的问题"+"改进方向"，而非打分表
3. **业务视角**：站在真实业务场景和用户视角评审，而非文档格式视角
4. **ToB经验**：运用ToB产品典型失败模式（权限遗漏、审批死角、数据口径混乱、角色边界模糊）评审

评审维度（按产物类型侧重）：
1. **设计合理性**：功能划分是否合理？模块边界是否清晰？有无冗余或缺失？
2. **业务逻辑完备性**：审批流是否覆盖所有场景？状态流转有无死锁？数据口径有无矛盾？
3. **用户体验可行性**：操作流程是否符合真实用户习惯？有无步骤过长或认知负担过重？
4. **风险识别**：有无遗漏的异常场景？有无安全风险？有无数据一致性风险？
5. **可落地性**：描述是否足够具体可直接指导研发？还是过于模糊需要二次解读？
6. **完整性**：是否覆盖了必要内容？（此维度权重较低，内部门禁已覆盖）

评审输出格式（必须严格遵循）：
```
## 评审结论：✅通过 / ❌不通过 / ⚠️通过但需关注

## 总评分（0-100）：<分数>

## 发现的问题（核心产出，按严重程度排序）：

### 🔴 严重问题（必须修复，否则不通过）
1. <问题描述> → <影响：为什么这是个问题> → <改进方向：具体怎么修>
2. ...

### 🟡 需关注问题（建议修复，不阻塞但影响质量）
1. <问题描述> → <影响> → <改进方向>
2. ...

### 💡 优化建议（锦上添花，提升设计水准）
1. <建议描述> → <预期收益>
2. ...

## 各维度评分：
- 设计合理性：<分数>/20
- 业务逻辑完备性：<分数>/20
- 用户体验可行性：<分数>/20
- 风险识别：<分数>/20
- 可落地性：<分数>/20
- 完整性：<分数>/20（权重较低，满分20而非25）

## 迭代建议（如不通过或⚠️通过）：
1. <具体改进项，指向问题编号>
2. ...
```

通过标准：
- ✅通过：总分 ≥ 75，无🔴严重问题
- ⚠️通过但需关注：总分 ≥ 75，但有🔴严重问题≤1个且可快速修复
- ❌不通过：总分 < 75，或🔴严重问题 ≥ 2个
```

### 3.3 各步骤评审维度侧重

不同产物类型的评审侧重不同，以下为每个步骤指定重点评审维度和典型问题方向：

| Step | 产物 | 重点评审维度 | 典型质疑方向 |
|------|------|-------------|-------------|
| Step 2 | 01-discovery.md | 设计合理性(40%) + 业务逻辑(30%) | 角色识别是否遗漏？场景覆盖是否偏窄？成功指标是否可量化？业务痛点是否抓准？ |
| Step 3 | 02-competitive-research.md | 设计合理性(40%) + 可落地性(30%) | 借鉴功能是否与客户真实场景匹配？差距分析是否过于乐观？建议补充是否优先级合理？ |
| Step 4 | discovery追问补充 | 业务逻辑(40%) + 风险识别(30%) | 阻塞维度答案是否真正解决了审批/权限问题？默认假设是否会产生二义性？ |
| Step 4.5 | 03-requirement.md | 设计合理性(30%) + 业务逻辑(30%) + 可落地性(20%) | 需求描述是否具体到字段级？验收指标是否可测试？章节裁剪是否遗漏关键需求？ |
| Step 5 | 04-prd.md | 设计合理性(30%) + 业务逻辑(30%) + 用户体验(20%) | 功能优先级划分是否合理？模块边界是否清晰？P0功能是否构成最小闭环？竞品功能融入是否生硬？ |
| Step 7 | 06+07 | 业务逻辑(40%) + 设计合理性(30%) | DAG依赖是否有遗漏或冗余？审批流是否有死锁场景？状态定义是否有歧义？构建顺序是否可执行？ |
| Step 8 | 08-page-spec.md | 用户体验(35%) + 设计合理性(30%) + 可落地性(20%) | 页面布局是否符合操作习惯？字段排列是否符合认知流程？角色视图分区是否遗漏关键差异？筛选条件是否覆盖实际查询场景？ |
| Step 9 | 10-permission-matrix.md | 业务逻辑(40%) + 风险识别(30%) | 权限是否有死角（能看不能操作/能操作但看不到数据）？数据隔离规则是否有漏洞？审批权限是否覆盖所有层级？ |
| Step 10 | 11-acceptance.md | 业务逻辑(35%) + 风险识别(30%) | 验收场景是否覆盖真实业务分支？边界条件是否遗漏关键异常？权限验收是否真正验证了隔离？ |
| Step 11 | 12+13 | 可落地性(40%) + 设计合理性(30%) | 任务粒度是否适中（过大难以追踪/过细管理成本高）？依赖关系是否真实反映了技术依赖？追踪矩阵是否有断链？ |

评审调用时，在用户提示中追加该步骤的重点评审维度和质疑方向，引导评审员聚焦核心问题而非泛泛打分。

## 4. 评审结果处理

### 4.1 通过（✅）

- 记录评审结果到 `14-review-log.md`
- 继续进入下一步

### 4.2 不通过（❌）

- 记录评审结果到 `14-review-log.md`
- 分析评审意见中的主要问题和改进建议
- 根据评审意见优化当前产物
- 重新执行内部质量门禁
- 重新调用外部大模型评审
- **最多重试 3 轮**：
  - 3 轮内通过：记录通过结果，继续下一步
  - 3 轮仍未通过：记录最终结果，向用户报告评审意见，由用户决定是否继续或人工修改

### 4.3 评审记录格式

评审日志 `14-review-log.md` 按 `templates/review-log.md` 模板格式生成和追加记录。核心要求：

1. **即时记录**：每层检查完成后立即追加，不等到全部完成
2. **四层全覆盖**：内部门禁、一致性检查、外部评审、人类QA确认（Step 4.5/8）全部记录
3. **问题编号唯一**：每个问题用 `P<Step序号>-<序号>` 编号（如 P2-001、P4.5-001），跨轮次延续
4. **修改内容必须具体**：不能只写"根据评审意见优化"，必须写明改了哪段内容、改成了什么
5. **人类反馈原文记录**：Step 4.5 和 Step 8 的用户反馈必须记录原文
6. **评审统计表+问题追踪汇总实时更新**：每次评审后更新末尾的两张汇总表

### 4.4 评审日志初始化

Step 2 开始前，按 `templates/review-log.md` 模板创建 `specs/<序号-功能名>/14-review-log.md`，写入项目信息头（项目名、产物目录、评审员配置列表）。后续每个 Step 的检查结果逐层追加到该文件。

## 5. 评审配置初始化

在 Step 1（需求输入）阶段，检查是否存在 `.cn-spec-kit-llm.json` 配置文件：

- **存在**：读取配置，加载评审员列表，用 `log()` 输出已注册的评审员信息
- **不存在**：用 `AskUserQuestion` 询问用户是否需要配置外部评审员：
  - 选项 1："不使用外部评审，仅依赖内部质量门禁"
  - 选项 2："配置外部评审员"
  
  如果用户选择配置评审员，继续询问 URL、Key、Model（可配置多个），并保存配置到 `.cn-spec-kit-llm.json`。

---

## 6. Guardrails

- 外部评审仅在内部质量门禁通过后触发，不替代内部门禁
- 评审调用失败（网络错误、API 错误等）时：跳过外部评审，仅依赖内部门禁继续，但需在 review-log 中记录失败原因
- 评审超时限制：每次评审调用最长 60 秒，超时视为评审失败
- 最多 3 轮重试，超过 3 轮必须让用户介入
- 评审员配置信息（尤其是 API Key）仅存储在 `.cn-spec-kit-llm.json`，不写入任何产物文档
- `.cn-spec-kit-llm.json` 不应提交到版本控制（建议加入 .gitignore）
- 所有评审记录写入 `14-review-log.md`，确保评审过程可追溯
