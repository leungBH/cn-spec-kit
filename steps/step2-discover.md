# Step 2: 需求发现 (discover)

## 执行步骤

1. 读取 `references/tob-patterns.md` 了解 ToB 产品分析框架
2. 生成 `01-discovery.md`（需求发现），写入 `specs/<序号-功能名>/` 目录
3. 在 `01-discovery.md` 开头记录需求原文

**序号规则**：查找 `specs/` 目录下已有子目录的最大序号，+1。如果 `specs/` 不存在则从 `001` 开始。功能名取英文 kebab-case（从需求中提取核心业务对象）。

## 目录创建

```bash
mkdir -p "specs/<序号-功能名>"
```

## discovery.md 必须包含的 9 个维度

| 维度 | 内容 |
|------|------|
| 需求原文 | 用户输入的一句话需求/访谈纪要原文 |
| 客户行业 | 行业名称、典型特征。识别行业后，检查 `presets/<industry>/` 是否有对应行业预设 |
| 客户规模 | 组织层级（集团/分公司/部门）、用户规模 |
| 业务目标 | 为什么要做这个系统、解决什么痛点 |
| 核心角色 | 谁会使用（列出角色名 + 职责概述） |
| 业务场景 | 主要操作场景列表（3-8 个） |
| 项目范围 | 一期做什么、二期可能做什么 |
| 成功指标 | 怎么判断系统做成功了 |
| 🔴 审批流程 | 业务是否涉及审批？审批层级？审批人确定规则？（硬阻塞维度） |
| 🔴 权限层级 | 是否有集团/分公司/部门多层权限？数据归属按什么口径？（硬阻塞维度） |

> 审批流程和权限层级是**硬阻塞维度**——必须获得明确答案才能继续，不能假设或跳过。如果用户无法回答，给出 2-3 个典型方案供选择。例如：
> "审批流程您暂时不确定，以下是同类产品的典型模式：A)金额阈值分级审批 B)按组织层级审批 C)单人审批。建议先选一个作为一期方案，二期再调整。"

## 非阻塞维度（软追问，最多 3 轮）

以下 4 个维度可以软追问，3 轮内无法获得明确答案则做合理默认假设：

1. **数据口径**：金额含税不含税？统计口径？（默认：不含税，按自然月）
2. **部署方式**：公有云还是私有化部署？（默认：公有云SaaS）
3. **集成系统**：需要对接钉钉/企微/飞书/OA/ERP？（默认：一期不对接，二期预留接口）
4. **报表需求**：需要哪些报表？导出格式？（默认：基础统计报表+Excel导出）

## 追问时结合竞品调研

Step 3 竞品调研完成后，如果发现了我们缺失的功能，回到 `01-discovery.md` 的"需求追问补充"章节追加竞品驱动的追问结果。

## 🚪 质量门禁

### 第一层：步骤完整性门禁

检查 01-discovery.md 是否覆盖上述 9 个维度：
- 🔴 审批流程、权限层级必须有明确结论——缺失任何一个 → ❌ 阻塞，不能进入下一步
- 非阻塞维度 4 个中至少 3 个有结论（含默认假设），缺失 ≥ 2 个 → ⚠️ 需确认
- 其余 7 个维度缺失 ≤ 1 个：✅ 通过；缺失 ≥ 2 个维度：❌ 不通过，回到本步补充

### 第二层：外部大模型评审

内部门禁通过后，触发外部大模型评审（详见 `steps/external-review.md`）：

- 评审维度：9维度覆盖完整性、业务理解准确性、角色识别合理性、场景描述充分性、阻塞维度回答的明确性
- 通过标准：总分 ≥ 75 且无严重问题
- 不通过：根据评审意见优化 discovery，最多重试 3 轮
- 评审结果记录到 `10-review-log.md`

外部评审通过后，才能进入 Step 3。
