# Step 7: 功能依赖 DAG + 业务流程 (flow)

本步骤生成两个产物：功能依赖 DAG 和业务流程文档。

---

## Part A: 功能依赖 DAG

读取 `04-prd.md` 和 `05-scope-selection.md`，识别选定功能模块之间的依赖关系。

### 依赖关系分析维度

1. **数据依赖**：模块 B 需要模块 A 的数据作为输入（如"余额管理"依赖"充值管理"产生的余额数据）
2. **流程依赖**：模块 A 的状态变更触发模块 B 的操作（如"充值审批通过"触发"余额增加"）
3. **权限依赖**：模块 A 的操作需要模块 B 中定义的角色/权限
4. **页面依赖**：模块 A 的页面跳转到模块 B 的页面

### DAG 格式

生成 `specs/<序号-功能名>/06-dependency-dag.md`，包含：

1. **Mermaid 依赖关系图**（使用 `graph TD` 语法）：
   ```mermaid
   graph TD
     套餐管理 --> 充值管理[数据:套餐价格]
     充值管理 --> 余额管理[流程:充值通过→余额增加]
     余额管理 --> API_Key管理[数据:余额阈值→Key限速]
     充值管理 --> 退款管理[流程:退款→余额回退]
     渠道分销 --> 充值管理[数据:折扣价计算]
     余额管理 --> 用量监控[数据:余额扣减→用量统计]
     用量监控 --> 报表中心[数据:用量数据→报表]
     API_Key管理 --> 用量监控[数据:Key调用量]
   ```

2. **依赖关系矩阵表**（表格：依赖模块 | 被依赖模块 | 依赖类型 | 依赖说明 | 影响范围）

3. **构建顺序建议**：基于 DAG 计算构建顺序（拓扑排序），标注哪些模块可并行开发

### DAG 的用途

- 影响后续研发任务的拆解顺序和依赖关系
- 帮助用户理解哪些模块必须先做、哪些可以并行
- 一致性检查时验证页面跳转关系是否与 DAG 一致

## Part B: 业务流程

读取业务流程模板（按覆盖优先级查找）：
- 先查 `overrides/business-flow.md`
- 再查 `presets/<industry>/business-flow.md`
- 最后 `templates/business-flow.md`

读取 `04-prd.md`、`06-dependency-dag.md` 和 `05-scope-selection.md` 获取功能清单、依赖关系和开发范围。

只对选定优先级的功能模块生成详细流程。未选定模块简要标注"二期规划"。

生成 `specs/<序号-功能名>/07-business-flow.md`。

### 每个选定功能模块必须包含

1. **流程总览**：Mermaid 状态流转图（用 `stateDiagram-v2` 语法）
2. **状态定义表**：每个状态的名称、可操作角色、可执行操作、变更条件
3. **审批规则**（如涉及审批）：
   - 审批层级和审批人确定规则
   - 退回规则（退回到哪一步、退回后是否可修改重提交）
   - 撤回规则（提交后能否撤回、撤回条件）
   - 超时规则（审批超时如何处理）
4. **通知规则**：状态变更时的消息通知对象和方式

### ToB 审批流典型模式

参考 `references/tob-patterns.md`：
```
草稿 → 提交 → 部门主管审批 → 财务审批 → 总经理审批 → 归档
                 ↘ 退回修改 ←———————————————↙
```

## 贪量门禁

### 第一层：步骤完整性门禁

检查：
- DAG 是否覆盖所有选定模块间的依赖关系
- 每个选定模块是否包含上述 4 个要素
- DAG 构建顺序是否合理（无循环依赖）
- 缺失要素 ≥ 2 个回到本步补充

### 第二层：外部大模型评审

内部门禁通过后，触发外部大模型评审（详见 `steps/external-review.md`）：

- 评审维度：依赖关系合理性、流程完整性、审批规则完备性、状态定义清晰度、构建顺序可执行性
- 通过标准：总分 ≥ 75 且无严重问题
- 不通过：根据评审意见补充 DAG 或业务流程，最多重试 3 轮
- 评审结果记录到 `14-review-log.md`

外部评审通过后，才能进入 Step 8。
